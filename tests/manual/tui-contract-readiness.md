# Разбор: отложенный TUI не потребует изменения контрактов (BEH-41)

DEL-55. Ручная проверка готовности контрактов `log.jsonl` и `state.json` к
отложенному TUI. Вывод: статус текущей задачи — **этап, номер попытки, исход** — и её
лог восстанавливаются из уже существующих полей, форматы не меняются (версии схем
остаются `1.0`). Источники: `schemas/log-schema.md`, `schemas/state-schema.md`.

## Что должен показывать TUI

1. Текущая задача и её статус.
2. Этап, на котором она сейчас находится.
3. Номер идущей попытки.
4. Исход: последней завершённой попытки и задачи в целом.
5. Лог задачи (поток событий), в том числе во время работы прогона.

## Откуда берётся каждый элемент

| Элемент | Источник | Поле |
|---|---|---|
| Задача в работе | `state.json` | `cursor.task_id` (и `tasks[].status == in_progress`) |
| Номер идущей попытки | `state.json` | `cursor.attempt`; запасной путь — `attempt` последнего `attempt_started` без `attempt_finished` в `log.jsonl` |
| Этап | `log.jsonl` | `stage` последней записи `step_finished`/`stage_started` по задаче: `implement` → `review` → `tests` |
| Исход последней попытки | `state.json` | `tasks[].last_attempt` (`number`, `success`, `error_code`) |
| Исход последней попытки (детали) | `log.jsonl` | `attempt_finished`: `success`, `error_code`, `decision`, `review_approved`, `tests_returncode` |
| Исход задачи | `log.jsonl` | `task_finished`: `success`, `error_code`, `attempt`, `attempts_total` |
| Прогон завершён / пауза | `state.json` | `finished`, `reason` |
| Лог задачи | `log.jsonl` | записи с нужным `task_id`, упорядоченные по `seq` |

Лог читается только добавлением в конец и сбрасывается на диск сразу, поэтому TUI
может хвостить файл, не мешая раннеру. Состояние перезаписывается атомарно
(временный файл, fsync, rename), поэтому читатель не увидит наполовину записанный
документ. Оба файла читаются без участия раннера и без его процесса.

## Проверка по шагам

Выполняет ревьюер перед закрытием BEH-41.

- [ ] Запустить прогон с фейковыми портами или взять каталог `logs/` готового прогона.
- [ ] Взять `state.json` посреди попытки (после `attempt_started`). `cursor` непуст;
      из него читаются задача и номер попытки.
- [ ] В `log.jsonl` найти последнюю запись `step_finished` этой задачи: её `stage`
      даёт текущий этап (до первого шага — этап `implement` по порядку цикла).
- [ ] После `attempt_finished` в `state.json` проверить `tasks[].last_attempt` и
      сверить с `attempt_finished` в журнале: `success`, `error_code` совпадают.
- [ ] После `task_finished` сверить `tasks[].status` и поля исхода задачи.
- [ ] Прервать прогон по Ctrl-C: задача `in_progress`, `cursor` указывает на неё,
      `reason == interrupted`; TUI показывает паузу без дополнительных полей.
- [ ] Убедиться, что `schema_version` обоих файлов по-прежнему `1.0` и в схемах нет
      правок, добавленных ради TUI.

## Известные ограничения (контракты не меняются)

- Внутришаговых засечек нет (схема состояния): внутри этапа TUI видит только границы
  шагов. Живой прогресс токенов (Q-14) в схемы не входит; когда он появится, это
  минорное расширение `1.x`, читатель мажора 1 его принимает.
- Этап идущей попытки выводится из журнала, а не из `state.json`: `cursor` хранит
  задачу и попытку, но не этап. Это чтение двух существующих файлов, не новое поле.

## Критерий приёмки

Все пункты чек-листа отмечены, а список нужных TUI данных закрыт таблицей выше без
новых полей и без смены мажора схем. Если для какого-то пункта нужного поля нет, это
дефект контракта: фиксируется отдельной задачей с повышением версии схемы, а BEH-41
не закрывается.
