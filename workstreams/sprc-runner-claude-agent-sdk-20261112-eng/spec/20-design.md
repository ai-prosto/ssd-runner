# Дизайн — sprc-runner на Claude Agent SDK

## 1. Назначение документа

Документ закрывает архитектурные вопросы, оставленные требованиями
(`10-requirements.md`, версия 2, approved), и задаёт механику, которой поведенческие
сценарии (`15-behaviour-spec.md`, версия 2, approved) становятся реализуемыми под TDD.
Верхние источники — только эти два узла; устав и дискавери видны через них.

Границы этого узла:

- продуктовые решения требований не пересматриваются; продуктовые вопросы Q-01 … Q-06
  и Q-14 остаются открытыми и здесь не решаются — для каждого из них фиксируется шов,
  через который ответ входит в реализацию, не меняя контрактов;
- код построчно не пишется: ниже названы модули, функции-границы, формы инвокаций,
  формы коммитов и состав эвиденции, но не их реализация;
- новых вопросов документ не вводит.

Инструмент — новый проект в соседнем репозитории; из spec-runner переносится только формат
`tasks.md` (CON-14, FR-10). Поэтому «точки врезки» ниже — это точки в создаваемой структуре,
а не правки существующего кода.

## 2. Резолюции открытых вопросов

Входной набор — архитектурные вопросы раздела 8 требований: Q-07 … Q-13.

#### Q-07 · owner_role: architects · resolution: resolved

Состояние прогона — один документ `state.json` в каталоге прогона, перезаписываемый целиком
атомарно (запись во временный файл рядом, fsync, переименование), плюс журнал `log.jsonl`
как append-only история. Разделение ролей обязательно: состояние отвечает на вопрос «что
делать дальше», журнал — на вопрос «что происходило», и дублирование между ними запрещено
(журнал не читается при возобновлении). Схема состояния: версия схемы, идентификатор прогона,
отпечаток входного описания, снимок применённой конфигурации, список этапов со статусом
и применённой моделью, список задач с полями `task_id`, `status` из закрытого набора
`pending | in_progress | done | failed`, числом сделанных попыток, описанием последней попытки
и ссылкой на коммит, курсор прогона и признак завершения с кодом причины. Гранулярность
чекпойнта — не реже, чем требует BEH-29, и на одну засечку чаще: состояние пишется при старте
прогона, при завершении этапа, при взятии задачи в работу, при старте попытки, при завершении
попытки, при завершении задачи и при постановке на паузу. Засечка «при старте попытки» нужна
не для возобновления, а для BEH-17: после Ctrl-C в середине попытки по файлам видно, какая
задача была прервана. Внутришаговый чекпойнт (после реализации, после ревью) сознательно
не вводится: прерванная попытка при возобновлении выполняется заново с начала, потому что
критерий успеха задачи неделим (BEH-19, BEH-42) и половина попытки не является пригодным
состоянием; хранить то, что никогда не используется для продолжения, значит нарушить CON-15
и RK-01.

#### Q-08 · owner_role: architects · resolution: resolved

Носитель журнала — JSONL: одна запись-событие на строку, только добавление в конец. Носитель
выбран не из вкуса, а из BEH-06: единый JSON-документ требует перезаписи файла на каждом
событии и после аварийной остановки оставляет либо устаревшую, либо битую версию, тогда как
дописывание строки сохраняет всё, что успело завершиться. Общий конверт каждой записи:
версия схемы, идентификатор прогона, порядковый номер, отметка времени, тип события,
и — там, где они определены — этап, `task_id`, номер попытки, идентификатор применённой
модели. Словарь типов событий закрыт: старт и завершение прогона, старт и завершение этапа,
старт задачи, старт попытки, завершение шага (реализация, ревью, тесты), вердикт проверки
диффа, завершение попытки, завершение задачи, пауза прогона. Длительности пишутся на событиях
завершения как явные поля, а не вычисляются читателем из разности отметок, иначе BEH-05
становится проверкой арифметики теста, а не контракта. Полнота полей FR-06 и BEH-24
обеспечивается не вторым писателем «итогов по задаче», а проекцией: единственный писатель —
журнал событий, а поставляемый с инструментом читатель собирает из событий строку по задаче
и сам является тем «единым парсером», о котором говорит BEH-26. Версионирование: поле версии
схемы в каждой записи плюс описание формата отдельным версионированным документом
в репозитории инструмента; добавление поля — минорное расширение, изменение смысла
или удаление поля — новая версия схемы. Продуктовый вопрос Q-14 (токены и стоимость)
этим решением не предрешён: такие поля, если ответ будет «да», добавляются в полезную
нагрузку событий этапа и попытки как необязательные, без смены версии словаря событий.

#### Q-09 · owner_role: architects · resolution: resolved

Защита готового кода (NFR-02) строится на трёх уровнях, и сторож — раннер, а не агент.
Первый уровень: каждая попытка начинается от последнего зафиксированного состояния рабочего
каталога, а неуспешная попытка откатывается к нему, так что мусор попыток не накапливается
и не выглядит как «удаление» на следующем шаге. Второй уровень, основной: перед фиксацией
изменений раннер берёт дифф рабочего каталога относительно последнего коммита и выносит
вердикт по закрытому набору нарушений — удаление файла, значимое сокращение содержимого
файла, выход изменения за пределы разрешённых путей, попадание секрета в дифф. Вердикт
выносится чистой функцией ядра над структурированной сводкой диффа (список путей, статус
изменения, числа добавленных и удалённых строк), поэтому проверяем без git и без сети (NFR-04).
Третий уровень: ограничение инструментов и путей агента средствами SDK — как предотвращение,
но не как доказательство (см. Q-11). Критерий «значимого сокращения» берётся из реализации
spec-runner, как прямо требует приёмка NFR-02: это перенос уже существующего порога
в параметры функции-вердикта, а не новое проектное решение, и исполнитель обязан перенести
его значением из соседнего репозитория, а не придумать своё. Проверяемость (RK-09):
нарушение конструируется тестом как сводка диффа — ядро выносит вердикт без файловой
системы; и отдельно на стыке проверяется, что при отрицательном вердикте коммит не
происходит, причина попадает в журнал попытки, а попытка считается неуспешной (BEH-32, BEH-34).

#### Q-10 · owner_role: architects · resolution: resolved

Детектирование исчерпания лимитов — ответственность адаптера SDK и только его. Адаптер
переводит отказы SDK в закрытый набор доменных исходов инвокации: выполнено, отказ
по лимитам подписки, отказ по транспортной ошибке, отказ по неверной конфигурации вызова,
прочий отказ. Сопоставление «сигнатура отказа SDK → доменный исход» живёт одной таблицей
в адаптере и тестируется подачей синтетических отказов, поэтому точная сигнатура отказа
запиненной версии SDK (NFR-10) — предмет сверки с ней при реализации, а не открытый
архитектурный вопрос: при смене версии SDK (RK-12) правится одна таблица. Стратегия паузы
для первой версии — немедленная остановка с сохранением состояния: исход «лимиты»
поднимается из адаптера в цикл, прогон ставит чекпойнт, печатает причину без трассировки
стека и выходит с кодом аварийной остановки. Это именно то, что фиксируют уже одобренные
BEH-31 и BEH-16, и ожидание с повтором их бы нарушило: ожидание неотличимо от зависания
в терминале (FR-04) и не даёт ненулевого кода возврата. Ожидание с повтором остаётся
расширением: политика паузы — отдельная точка решения в цикле, читающая конфигурацию,
поэтому добавление режима «ждать и повторить» становится новым значением ключа, а не
переделкой цикла, журнала или состояния.

#### Q-11 · owner_role: architects · resolution: resolved

Изоляция (NFR-05) — комбинация, с явным разделением ролей. Средствами SDK задаются рабочий
каталог инвокации и допустимый набор инструментов — это предотвращение, которое снижает
вероятность выхода за периметр. Доказательством же изоляции служит проверка раннером:
вердикт по диффу перед коммитом (Q-09) плюс единственный допустимый корень записи —
целевой каталог. Опора только на SDK недопустима по тому же принципу, которым требования
уже руководствуются в NFR-07: исход определяет раннер, а не заявление или настройка
на стороне модели; ограничение инструментов нельзя предъявить как эвиденцию и нельзя
проверить тестом ядра без сети. Технически единственный корень записи получается
из размещения: каталог прогона лежит внутри целевого каталога (§3.2), все операции git
выполняются с явным указанием этого корня, а предикат допустимости пути — чистая функция
ядра. Файлы DarkFactory (CON-07) защищены двумя уровнями вердикта, а не одним. Первый
уровень — названный инвариант: любой путь вне `<target>` недопустим, поэтому при целевом
каталоге, не содержащем эти пути, они недостижимы по построению. Второй уровень —
безусловный предикат: пути CON-07 (`profiles/`, `scripts/review/`,
`spec-runner.config.yaml`, `.github/`) недопустимы для записи и для индексирования
независимо от того, какой каталог задан как `<target>`, в том числе когда целевым
каталогом указан репозиторий, который их содержит. Второй уровень обязателен, потому
что NFR-05 и BEH-33 требуют неизменности этих файлов «ни при каких условиях»,
а `<target>` задаётся параметром пользователя (§3.2) и потому не может нести такое
условие в одиночку: первого уровня достаточно для посторонних файлов каталога запуска,
но не для случая `<target>`, накрывающего пути CON-07. Поэтому список CON-07 перестаёт
быть только негативным набором данных и становится частью вердикта: перечень живёт явным
значением в `core/layout.py`, применяется чистой функцией `core/guard.py` вместе
с предикатом «внутри `<target>`» (вердикт — конъюнкция обоих) и проверяется прогоном,
в котором `<target>` накрывает файлы DarkFactory (раздел 4, рамка BEH-33).

#### Q-12 · owner_role: architects · resolution: resolved

Команда запуска тестов берётся из конфигурации — обязательный ключ с разумным значением
по умолчанию для стека сгенерированного проекта. Обнаружение по структуре проекта
отклонено: оно делает фактическую команду зависящей от содержимого рабочего каталога,
то есть вводит второй источник настроек прогона, что прямо запрещает приёмка FR-01
и сценарий BEH-02, и лишает журнал воспроизводимости — по записи нельзя восстановить,
что именно запускалось. Указание команды в тексте задачи отклонено по NFR-07: тогда
команду выбирает модель, и утверждение модели снова начинает влиять на исход. Фактически
применённая команда и её код возврата пишутся в событие шага тестов (BEH-21), запуск
выполняется адаптером-раннером тестов, который возвращает ядру код возврата и ссылку
на сохранённый вывод; ядро решает исход по коду возврата и ничего не парсит из вывода.

#### Q-13 · owner_role: architects · resolution: resolved

Граница адаптера SDK — узкий протокол из двух операций: выполнить инвокацию этапа
и закрыть сессию/освободить ресурсы. Инвокация принимает значение-запрос (этап, модель,
собранные входные тексты, рабочий каталог, допустимые инструменты, ограничение
по длительности) и возвращает значение-результат (доменный исход из набора Q-10, текст
ответа, ссылка на сохранённый транскрипт, причина остановки, необязательные сведения
об использовании). Ядро не видит ни типов SDK, ни исключений SDK, ни понятия «сообщение»;
всё, что переходит границу, — простые значения, пригодные для записи в журнал. Протокол
объявлен в модуле портов рядом с портами файловой системы, git, раннера тестов и часов;
импорт `claude_agent_sdk` встречается ровно в одном модуле-адаптере (BEH-36). Подмена
в тестах — не монкипатч и не мок библиотеки, а вторая реализация протокола, внедряемая
в точке сборки: подставной агент возвращает заранее заданные исходы, считает инвокации
и умеет имитировать отказ по лимитам. Этого достаточно для BEH-35: тесты ядра проходят
без сети и ключей, а запрет прямых вызовов SDK, git и сетевых клиентов в ядре проверяется
инспекцией кодовой базы и импортом ядра при недоступном модуле SDK. Шов ревьюера
(продуктовый Q-03) реализован тем же приёмом: ревью — отдельный порт, и любой из трёх
возможных ответов (та же модель, другая модель Claude, детерминированная проверка) —
это его реализация; идентификатор исполнителя ревью пишется в журнал, поэтому ответ
на Q-03 не меняет ни порядок шагов (BEH-18), ни критерий успеха (BEH-19), ни контракт
журнала.

## 3. Механика

### 3.1 Точки врезки: модули и функции-границы

Создаваемая структура репозитория инструмента; в скобках — назначение границы.

- `cli.py` — разбор аргументов, выбор команды, печать прогресса, коды возврата.
  Функции-границы: сборка состава прогона из конфигурации и портов (единственная точка,
  где создаются реальные адаптеры), обработчик команды `run`, обработчик команды `resume`.
- `config.py` — чтение единственного файла настроек и его валидация до старта: функция
  загрузки, возвращающая либо значение конфигурации, либо перечень проблемных ключей
  по имени (BEH-03). Неизвестный ключ — ошибка, а не предупреждение.
- `core/run.py` — жизненный цикл прогона: последовательность этапов подготовки, затем
  обход списка задач. Функции-границы: выполнить прогон, продолжить прогон от состояния.
- `core/task_cycle.py` — одна попытка и правило повторов: функция выполнения попытки
  (реализация → ревью → тесты → вердикт диффа) и функция критерия успеха задачи
  (BEH-19, BEH-42 — один критерий, одна функция, без второго места принятия решения).
- `core/state.py` — модель состояния и чистые переходы над ней; функция «следующая
  невыполненная задача» (BEH-30).
- `core/logbook.py` — конструирование записей журнала (чистое) и функция-проекция
  «события → строка по задаче», она же проверка полноты полей FR-06.
- `core/guard.py` — чистые вердикты: допустимость пути (конъюнкция «внутри `<target>`»
  и «не в перечне безусловно запрещённых путей CON-07», Q-11), удаление и сокращение
  файлов, присутствие секрета в диффе.
- `core/layout.py` — чистые функции размещения: целевой каталог по параметру или
  по умолчанию, путь каталога прогона внутри него, разделение путей на «продукт»
  и «служебные» (§3.2), а также перечень безусловно запрещённых путей CON-07 и его
  разрешение относительно корня устава. Единственное место, где это разделение
  и этот перечень вычисляются.
- `core/tasks_md.py` — чтение и простановка отметки в `tasks.md` в формате spec-runner
  (FR-10): внешний контракт, вынесенный в отдельный модуль, чтобы его проверка не зависела
  от остального.
- `ports.py` — протоколы: агент (Q-13), файловая система, git, раннер тестов, часы,
  ревьюер (шов Q-03).
- `adapters/claude_sdk.py` — единственный модуль с импортом SDK и таблицей классификации
  отказов (Q-10). `adapters/git.py`, `adapters/fs.py`, `adapters/tests.py`,
  `adapters/clock.py` — тонкие реализации остальных портов.
- `schemas/` — версионированные описания формата журнала и формата состояния (NFR-08).

### 3.2 Размещение: целевой каталог, каталог прогона, отслеживаемость

Размещение задано одной иерархией, из которой следуют и инвариант изоляции, и поведение
коммита, и поведение откката; формулируется она так, чтобы быть одинаково верной
и при заданном целевом каталоге, и без него.

- **Целевой каталог** (`<target>`) — единственный корень записи и корень git-репозитория
  прогона. Задаётся параметром команды; при отсутствии параметра это `.sdd-runs/` внутри
  каталога запуска, то есть `<target> = <cwd>/.sdd-runs/` (FR-08, BEH-13). Иных различий
  между «с параметром» и «без параметра» нет: дальше весь дизайн говорит только
  о `<target>`.
- **Продуктовые пути** — код и тесты сгенерированного проекта; лежат в `<target>`
  и отслеживаются git. Только они попадают в коммиты и только они откатываются.
- **Каталог прогона** — `<target>/.sprc/<run_id>/`. Лежит внутри `<target>`, поэтому
  вердикт о допустимости пути (Q-11) один и тот же для продукта и для служебных файлов:
  первый его предикат — любой путь вне `<target>` недопустим; второй предикат задан
  следующим пунктом. При этом `.sprc/` внесён в `.gitignore`
  репозитория `<target>` (файл создаёт или дополняет раннер при инициализации прогона),
  поэтому каталог прогона — внутри корня записи, но вне отслеживаемых git путей.
- Репозиторий каталога запуска не используется никогда: все операции git выполняются
  с явным указанием корня `<target>`. Когда `<target>` по умолчанию лежит внутри чужого
  репозитория, это именно то, что защищает посторонние файлы каталога запуска
  (BEH-13) — они вне `<target>` и потому недостижимы по построению. Случай, когда
  `<target>` указан так, что сам содержит файлы DarkFactory, этим не закрывается
  и закрывается следующим пунктом.
- **Безусловно запрещённые пути** — перечень CON-07 (`profiles/`, `scripts/review/`,
  `spec-runner.config.yaml`, `.github/`). Они недопустимы для записи и для
  индексирования при любом `<target>`, поэтому вердикт о пути — конъюнкция двух
  предикатов: «внутри `<target>`» и «не в перечне CON-07» (Q-11, NFR-05, BEH-33).
  Перечень задан в `core/layout.py` значением, разрешается относительно корня, в котором
  его определяет устав, и применяется до каждой записи раннером и до индексирования,
  а не только при итоговой проверке прогона.

Из этой иерархии прямо следуют три утверждения, на которые опираются §3.4 и раздел 4:
служебные артефакты прогона не попадают в коммит (они игнорируются git, а индексируются
только продуктовые пути); откат попытки их не затрагивает (откат работает по отслеживаемым
путям и не удаляет игнорируемые); изоляция доказуема двумя чистыми предикатами —
«внутри `<target>`» и «не в перечне CON-07» — без опоры на настройки SDK.

### 3.3 Формы инвокаций CLI

- `run` — принимает входное описание как текст или как путь к файлу (взаимоисключающе),
  необязательный целевой каталог, путь к конфигурации. Первым действием копирует входное
  описание в каталог прогона и больше его не трогает (BEH-12).
- `resume` — принимает путь каталога прогона и ту же конфигурацию; восстанавливает состояние,
  продолжает со следующей невыполненной задачи, завершённые задачи не перезапускает
  и их артефакты не перезаписывает (BEH-30).
- Коды возврата, три различимых исхода плюс отказ на старте (BEH-16, BEH-03): `0` — все
  задачи успешны; `2` — прогон дошёл до конца, есть неуспешные задачи; `3` — аварийная
  остановка или пауза (прерывание, сбой, лимиты подписки); `4` — отказ на старте
  по конфигурации. Значение `1` не используется, чтобы не смешиваться с аварийным
  завершением интерпретатора.
- Прогресс в терминал печатается по ходу: текущий этап либо `task_id`, номер попытки,
  исход предыдущей задачи (BEH-15). Поток прогресса и журнал — разные вещи: прогресс
  не является источником данных для анализа и не обязан совпадать с журналом по полям.

### 3.4 Формы инвокаций агента

Четыре формы инвокации соответствуют четырём этапам конфигурации (FR-01): подготовка спеки
и требований, составление списка задач, реализация кода, ревью. Все четыре — один и тот же
тип запроса и один и тот же тип результата (Q-13), различаются моделью, составом входных
текстов и допустимыми инструментами: подготовительные этапы пишут только в каталог прогона,
этап реализации — в продуктовые пути `<target>`, ревью не пишет вообще. Форматы порождаемых
артефактов подготовки задаются скиллом-источником (FR-11); до ответа на продуктовый Q-06
шов — ссылка на путь и версию источника в конфигурации, подставляемая в состав входных
текстов этапа; структура инвокаций от ответа не меняется.

### 3.5 Формы коммитов и состава эвиденции

Коммит — единица «успешно завершённая задача», один коммит на задачу, и только раннером.
Последовательность фиксации: выполнен критерий успеха задачи — нулевой код возврата
тестов, пройденное ревью и пройденные проверки спецификации задачи (BEH-19, BEH-42) →
вынесен положительный вердикт по диффу (Q-09), включающий оба предиката пути, так что
путь из перечня CON-07 даёт отрицательный вердикт даже когда лежит внутри `<target>`
(§3.2) → индексируются только продуктовые пути `<target>`, и из них исключаются пути
перечня CON-07, так что служебные артефакты прогона в коммит не попадают (они
и игнорируются git по §3.2, и не перечисляются при индексировании — два независимых
основания) → коммит.
Отрицательный вердикт останавливает коммит, причина пишется в журнал попытки, попытка
считается неуспешной (BEH-34). Неуспешная попытка откатывает к последнему коммиту только
отслеживаемые продуктовые пути и удаляет созданные попыткой неотслеживаемые файлы
продуктовых путей; игнорируемые пути, то есть `<target>/.sprc/`, откат не трогает.
Поэтому каталог прогона — `state.json`, `log.jsonl`, эвиденция — переживает откат попытки,
неуспешную задачу и аварийную остановку: записи журнала по завершённым задачам и попыткам
сохраняются (FR-02, BEH-06, BEH-22), состояние для возобновления не теряется (FR-09,
BEH-30). Отброшенный дифф сохраняется в эвиденции попытки — это делает следующую попытку
воспроизводимой и не даёт откату выглядеть потерей готового кода. Сообщение коммита несёт
`task_id`, номер попытки и короткое название задачи, а машиночитаемые сведения
(идентификатор прогона, номер попытки, код возврата тестов, исход ревью) — трейлерами;
журнал хранит идентификатор коммита по задаче.

Состав эвиденции каталога прогона, читаемый без запуска инструмента (BEH-25): неизменная
копия входного описания и её отпечаток; артефакты подготовки (спека, требования, `tasks.md`);
`state.json`; `log.jsonl`; по каждой попытке каждой задачи — транскрипт инвокаций, вывод
запуска тестов, вердикт ревью, сводка диффа и, если был откат, отброшенный дифф. Записи
журнала ссылаются на эти файлы относительными путями; крупные тексты в журнал не
встраиваются, чтобы запись оставалась разбираемой строкой.

### 3.6 Регламент приёма изменений в репозитории инструмента

NFR-11 («новая функция — с тестами, исправление — с регрессионным тестом») и сценарий
BEH-38 относятся не к поведению прогона, а к процессу работы над самим инструментом,
и механизм им назначается соответствующий — двухчастный, без автоматического гейта,
который требования в первой версии не вводят.

Первая часть — порядок работ: декомпозиция обязана выдавать задачи, начинающиеся
с падающего теста по рамкам раздела 4, а критерий готовности задачи инструмента включает
наличие теста, который до изменения падал. Для исправления дефекта регрессионный тест —
это и есть red-тест задачи, поэтому NFR-11 не добавляет отдельного шага, а фиксирует
уже принятый порядок.

Вторая часть — предъявляемый артефакт: чек-лист приёма изменений в репозитории инструмента
(`tests/manual/change-review-checklist.md` по BEH-38), перечисляющий проверки «есть
сопровождающий тест», «для дефекта есть тест, падавший до исправления», «ruff, pyrefly,
pytest зелёные» (BEH-37). Это ручная проверка по виду, назначенному сценарием, и дизайн
сознательно не превращает её в автоматический гейт: обязательность и способ регулярной
проверки на стороне CI оставлены требованиями открытыми (NFR-12, Q-05), а изобретать гейт
раньше этого ответа значит решать за продукт. Соблюдение NFR-11 при этом не ослабляется:
Must остаётся Must, носитель — названный чек-лист плюс порядок работ, и ничто в дизайне
не разрешает принимать изменение без теста.

## 4. Рамки red-дизайна

Общее правило для всего узла: red-тест обязан падать по той причине, которую называет
сценарий, и обязан остаться осмысленным после реализации. Проверки существования файла,
наличия каталога, имени модуля или факта вызова функции этому не удовлетворяют: они
зеленеют от заглушки. Ниже — рамки по типам задач.

**Задачи-контракты (журнал, состояние, `tasks.md`; BEH-04, BEH-05, BEH-21, BEH-24, BEH-26,
BEH-27, BEH-29).** Red-тест обязан проверять живьём: провести прогон на подставном агенте
и подставном раннере тестов, затем разобрать порождённый файл поставляемым читателем
и утверждать о значениях полей и их полноте по каждой задаче. Red-тест не должен: утверждать,
что `log.jsonl` или `state.json` существуют; сравнивать файл с золотым слепком, лежащим
рядом в репозитории (слепок фиксирует сегодняшнюю реализацию, а не контракт); строить запись
журнала в самом тесте и утверждать о собственной конструкции; проверять формат регулярным
выражением вместо разбора читателем.

**Задачи-замеры (BEH-05, BEH-21, BEH-39).** Red-тест обязан проверять живьём, что
длительности и код возврата берутся из зафиксированных на событиях значений при подставленных
часах и подставленном раннере тестов. Red-тест не должен: спать; утверждать «длительность
больше нуля»; зависеть от реального времени машины. Серия надёжности (BEH-39) остаётся
регламентом для человека с записью применённых моделей, автоматическим гейтом не становится:
десять живых прогонов в автотесте дают флаки и расход подписки, а не измерение.

**Задачи-размещение (BEH-13, BEH-33).** Red-тест обязан проверять живьём: при заданном
целевом каталоге и при его отсутствии продуктовые файлы оказываются внутри `<target>`,
каталог прогона — внутри `<target>/.sprc/`, посторонние файлы каталога запуска
и файлы DarkFactory не изменены, а коммит не содержит путей из `.sprc/`. Отдельным
обязательным случаем рамка требует прогон, где `<target>` задан так, что накрывает файлы
DarkFactory (`profiles/`, `scripts/review/`, `spec-runner.config.yaml`, `.github/`):
по завершении прогона — успешного, с неуспешной задачей и с аварийной остановкой — эти
файлы не изменены и не попали ни в один коммит, то есть проверяется именно безусловный
предикат, а не удачное взаимное расположение каталогов. Red-тест не должен: проверять
только строку пути, собранную функцией размещения, без фактического прогона; полагаться
на то, что служебные файлы не попали в коммит, только из-за `.gitignore`, не проверив
состав коммита; считать достаточным один прогон, где `<target>` лежит в стороне
от путей CON-07.

**Задачи-границы (BEH-35, BEH-36, BEH-14).** Red-тест обязан проверять живьём: ядро
импортируется и его тесты проходят при недоступном модуле SDK, отключённой сети
и отсутствующих ключах; инспекция кодовой базы находит импорт SDK ровно в одном модуле
и не находит вызовов codex и `claude -p`; версия SDK в описании зависимостей — точное
значение. Red-тест не должен: утверждать наличие каталога `adapters/` или соглашения
об именах; подменять границу монкипатчем вместо второй реализации протокола; принимать
за доказательство изоляции настройку инструментов на стороне SDK.

**Задачи-сторожа (BEH-32, BEH-33, BEH-34).** Red-тест обязан проверять живьём: на
сконструированном нарушении (удалённый файл предыдущей задачи, значимо сокращённый файл,
путь вне разрешённого корня, секрет в диффе) вердикт отрицателен, коммит не создан, причина
в журнале, попытка неуспешна; и симметрично — на безобидном изменении коммит создаётся.
Нарушение «путь вне разрешённого корня» конструируется в двух видах: путь вне `<target>`
и путь из перечня CON-07 внутри `<target>` — второй вид обязателен, иначе безусловный
предикат остаётся непроверенным. Red-тест не должен: утверждать, что функция-сторож была
вызвана; проверять только константу со списком разрешённых или запрещённых путей;
ограничиваться проверкой, что файлы DarkFactory существуют после прогона — нужен прогон,
который без сторожа их бы задел.

**Задачи-возобновление (BEH-06, BEH-17, BEH-30, BEH-31).** Red-тест обязан проверять живьём:
обрыв воспроизводится (между задачами, в середине попытки, после неуспешной попытки),
после обрыва состояние читаемо и консистентно, а возобновление доходит до конца списка,
причём подставной агент фиксирует ноль новых инвокаций по уже завершённым задачам. Red-тест
не должен: утверждать только о содержимом `state.json` без фактического продолжения
прогона; проверять, что сброс буфера был вызван, вместо чтения файла после обрыва;
имитировать лимиты подписки исключением типа SDK — отказ подаётся через подставную
реализацию протокола агента.

**Задачи-исходы (BEH-19, BEH-20, BEH-23, BEH-42).** Red-тест обязан проверять живьём, что
исход определяется кодом возврата, вердиктом ревью и проверками спецификации задачи,
а заявление агента об успехе исход не меняет, и что число попыток конечно и не превышает
лимит. Red-тест не должен: разбирать текст ответа модели; предрешать продуктовые ответы —
значение лимита по умолчанию и поведение после его исчерпания (Q-04), порог надёжности
(Q-02), исполнителя ревью (Q-03) и состав эталонного описания (Q-01) тест не фиксирует.

**Задачи-регламенты (BEH-37, BEH-38, BEH-40).** Это свойства репозитория и процесса,
а не поведения прогона (подтверждено допущением A-B4 и видами `integration` и `manual`).
Для BEH-37 и BEH-40 проверка живьём — фактический запуск ruff, pyrefly и pytest
на заявленном стеке с утверждением о коде возврата, а не чтение конфигурационных файлов
и не поиск строки `line-length = 88`. Для BEH-38 автоматического red-теста нет и не должно
быть: носителем служит чек-лист §3.6, предъявляемый при приёме изменения, и запрет
на автоматический гейт здесь означает только отсутствие CI-проверки до ответа на Q-05,
а не отсутствие проверки. Red-тест не должен: подменять BEH-38 метрикой покрытия; считать
достаточной проверку, что файл чек-листа существует.

## 6. Вне объёма

Дизайн сознательно оставляет исполнителю под TDD:

- текст промптов каждого этапа, их сборку и порядок входных фрагментов — при условии, что
  применённая модель и ссылка на транскрипт попадают в журнал;
- внутреннюю декомпозицию перечисленных модулей на функции ниже названных границ, имена
  приватных сущностей, выбор библиотеки сериализации, устройство фикстур pytest;
- имена полей журнала и состояния сверх обязательного состава FR-06 и схем раздела 2,
  а также точный вид строк прогресса и текстов сообщений об ошибках — требуется только,
  чтобы сообщение называло проблемный ключ (BEH-03) и причину паузы без трассировки (BEH-31);
- имя подкаталога прогона внутри целевого каталога как строку: инварианты «внутри
  `<target>` и вне отслеживаемых git путей» и «вне перечня CON-07» обязательны (§3.2),
  конкретное `.sprc` — соглашение; перечень путей CON-07 исполнителю не на выбор —
  он задан уставом и переносится значением;
- формулировки пунктов чек-листа приёма изменений (§3.6) сверх обязательных проверок
  NFR-11 и BEH-37;
- конкретное значение лимита попыток по умолчанию и команду тестов по умолчанию как числа
  и строки в конфигурации: механика их чтения задана (Q-10, Q-12), значения — настройка;
- порядок выполнения работ, разбивку на задачи и последовательность red-тестов — это этап
  декомпозиции;
- любой код: построчная реализация не входит в этот узел по правилам этапа.

Дизайн не решает и не вправе решать: продуктовые вопросы Q-01 … Q-06 и Q-14 — для каждого
выше назван шов, через который ответ входит без переделки контрактов; сравнение моделей
(OUT-01), иные харнессы (OUT-02, CON-01), TUI (OUT-03, FR-05) — последний учтён только как
ограничение «контракты журнала и состояния достаточны для него» (BEH-41).
