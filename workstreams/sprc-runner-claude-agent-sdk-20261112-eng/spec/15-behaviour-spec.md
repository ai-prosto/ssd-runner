# Поведенческая спецификация — sprc-runner на Claude Agent SDK

## 1. Назначение документа

Документ разворачивает требования (`10-requirements.md`, версия 2, approved) в наблюдаемые
сценарии поведения. Единственный верхний источник — узел requirements; устав и дискавери-брифы
видны только через него. Каждый сценарий описывает поведение, которое можно проверить
со стороны — по файлам в каталоге прогона, по выводу в терминал, по коду возврата и по логу —
без обращения к внутреннему устройству реализации.

Правила работы с идентификаторами:

- BEH-01 … BEH-43 вводятся этим документом и далее не перенумеровываются.
- Каждый сценарий трассируется в FR-/NFR-идентификаторы требований; новых требований
  документ не вводит и границы требований не расширяет.
- Если требование оставляет выбор за открытым вопросом (Q-01 … Q-14 требований), сценарий
  фиксирует наблюдаемую часть поведения и помечает зависимость строкой **depends_on**.
  Такой сценарий описывает, что должно быть видно снаружи, но не предрешает ответ на вопрос.

## 2. Соглашения

**Термины.** *Прогон* — одно исполнение инструмента над одним входным описанием.
*Каталог прогона* — каталог, куда инструмент пишет служебные артефакты (входное описание,
артефакты подготовки, состояние, лог). *Целевой каталог* — каталог, куда кладётся результат
(код и тесты); по умолчанию `.sdd-runs/` (FR-08). *Попытка* — один проход цикла
«реализация → ревью → тесты» по одной задаче (FR-07). *Этап* — подготовка спеки
и требований, составление списка задач, реализация кода, ревью (FR-01).

**Форма сценария.** Каждый сценарий — **Дано** / **Когда** / **Тогда**, где «Тогда»
содержит только внешне наблюдаемые следствия.

**Строка проверки.** `checked_by` указывает намеченную проверку: `status: planned` —
проверка ещё не написана; `kind` — вид проверки (`atp` — автотест на чистой логике ядра,
`contract` — проверка формата внешнего контракта, `integration` — проверка на стыке
с файловой системой, git или адаптером SDK, `e2e` — сквозной прогон CLI, `manual` —
проверка по регламенту человеком); `owner: qa`; `target` — путь проверки в репозитории
инструмента (соседнее репо), относительно его корня. Пути намечены этим документом
и уточняются при реализации без изменения смысла сценария.

**Периметр.** Сценарии BEH-01 … BEH-39, BEH-42 и BEH-43 входят в приёмку первой версии. BEH-40 относится
к требованию приоритета Should (NFR-12), BEH-41 — к отложенному TUI (FR-05); в приёмку
первой версии они не входят и помечены явно.

## 3. Сценарии: конфигурация прогона

#### BEH-01: Модель этапа берётся из конфигурации и применяется к этапу

`traces: [FR-01]`

**Дано** конфигурация прогона, в которой для каждого из четырёх этапов — подготовка спеки
и требований, составление списка задач, реализация кода, ревью — задан отдельный ключ модели.
**Когда** пользователь меняет значение ключа модели одного этапа и запускает прогон заново
без правок кода.
**Тогда** этот этап выполняется указанной моделью, остальные этапы — своими, а инструмент
не подменяет и не подбирает модель самостоятельно.

- **checked_by**: `status: planned` `kind: integration` `owner: qa` `target: tests/integration/test_stage_model_selection.py`

#### BEH-02: Все настройки прогона читаются из одного файла

`traces: [FR-01]`

**Дано** конфигурационный файл с моделями этапов, лимитом попыток, каталогами и параметрами
логирования.
**Когда** прогон запускается.
**Тогда** все перечисленные настройки взяты из этого файла, и ни одна настройка прогона
не читается из второго источника — ни из переменных окружения, ни из второго файла,
ни из значений, вшитых в код в обход файла.

- **checked_by**: `status: planned` `kind: atp` `owner: qa` `target: tests/unit/test_config_single_source.py`

#### BEH-03: Неполная конфигурация останавливает старт и называет проблемный ключ

`traces: [FR-01, FR-04]`

**Дано** один из трёх случаев: файла конфигурации нет; в файле есть неизвестный ключ;
модель какого-то этапа не заполнена.
**Когда** пользователь запускает прогон.
**Тогда** прогон не стартует — ни один этап не выполняется и ни одна задача не начинается;
в терминал печатается сообщение с именем проблемного ключа; код возврата ненулевой

- **checked_by**: `status: planned` `kind: atp` `owner: qa` `target: tests/unit/test_config_validation.py`

#### BEH-04: Фактически применённая модель каждого этапа видна в логе

`traces: [FR-01, FR-06, NFR-08]`

**Дано** завершённый прогон с разными моделями на разных этапах.
**Когда** лог прогона читается без повторного обращения к модели.
**Тогда** для каждого выполненного этапа и каждой попытки по задаче в логе присутствует
идентификатор фактически использованной модели, и он совпадает со значением

через адаптер SDK; выбор конкретной модели остаётся за ключом конфигурации

## 7. Сценарии: цикл реализации задачи

#### BEH-18: Шаги цикла выполняются в порядке реализация → ревью → тесты

`traces: [FR-07]`

**Когда** по ней выполняется попытка.

NFR-01 … NFR-12) имеет хотя бы один сценарий; каждый сценарий трассируется хотя бы
в одно существующее требование. Критерии приёмки первой версии (раздел 6 требований)
покрыты так: сквозной сценарий — BEH-11; цикл по всем задачам, соответствие спецификации и отметки —
BEH-18, BEH-19, BEH-22, BEH-28, BEH-42; полнота и единый парсер лога — BEH-24, BEH-26; возобновление — BEH-30;
надёжность — BEH-39; инструментарий качества и ядро без сети — BEH-35, BEH-37.

## 15. Допущения этого уровня

- **A-B1.** Допущения требований A-01 … A-04 действуют без изменений. Сценарии написаны так,
  чтобы расширение объёма первой версии до паритета с spec-runner (Q-01) добавляло задачи
  и тестовые данные, но не меняло формулировки сценариев и контракты BEH-24, BEH-26,
  BEH-27, BEH-29.
- **A-B2.** Эталонное входное описание (A-02 требований) существует к моменту написания
  проверок BEH-07, BEH-08, BEH-11, BEH-39; до его появления эти проверки остаются
  в состоянии `planned`.
- **A-B3.** Пути в `target` намечены для репозитория инструмента (соседнее репо) и могут
  уточняться при реализации; смена пути не меняет сценарий и не требует пересмотра
  этого узла.
- **A-B4.** Все сценарии наблюдаемы без доступа к внутренним структурам реализации —
  по файлам каталога прогона, выводу в терминал и коду возврата. Сценарии, требующие
  инспекции кодовой базы (BEH-36, BEH-37, BEH-38), проверяют свойства репозитория,
  а не поведения прогона, и отнесены к видам `atp`, `integration` и `manual` соответственно.

## 16. Открытые вопросы

Новых вопросов этот узел не вводит. Ниже — вопросы требований, которые влияют
на формулировку или на возможность написать проверку; в сценариях они указаны строкой
**depends_on**.

- **Q-01 · product · blocking: true.** Объём первой версии. Влияет на состав эталонного
  описания и на число задач в BEH-11; формы сценариев не меняет.
- **Q-02 · product · blocking: false.** Целевое значение надёжности. Влияет на порог
  в BEH-39; до ответа порог взят по формулировке NFR-01 — не менее 9 из 10.
- **Q-03 · product · blocking: true.** Исполнитель шага «ревью». Решение принято
  владельцем решения (P-02) и зафиксировано сценарием BEH-43: ревью выполняет модель
  Claude отдельной инвокацией через адаптер SDK, модель задаётся ключом `model_review`.
  Формальное закрытие вопроса — в узле требований. Влияет на реализацию
  BEH-18 и BEH-19, но не на наличие шага и не на критерий успеха задачи.
- **Q-04 · product · blocking: false.** Лимит попыток по умолчанию и поведение прогона
  после его исчерпания — остановка или переход к следующей задаче. Влияет на ожидаемое
  значение в BEH-23; сценарий проверяет только пометку задачи проваленной и отсутствие
  новых попыток, не предрешая ответ.
- **Q-05 · product · blocking: false.** Обязательность проверяемой поддержки Linux.
  Определяет, входит ли BEH-40 в регулярную проверку.
- **Q-06 · product · blocking: true.** Скилл-источник форматов артефактов подготовки.
  Без ответа BEH-09 не может быть написан как проверка — нет эталона формата.
- **Q-07 · architects · blocking: true.** Схема состояния прогона и гранулярность
  чекпойнта. Нужна для BEH-29.
- **Q-08 · architects · blocking: true.** Схема машиночитаемого лога. Нужна для BEH-04,
  BEH-05, BEH-21, BEH-24, BEH-26.
- **Q-09 · architects · blocking: true.** Механизм защиты готового кода. Нужен для BEH-32.
- **Q-10 · architects · blocking: true.** Детектирование исчерпания лимитов подписки
  и стратегия паузы. Нужны для BEH-31.
- **Q-11 · architects · blocking: false.** Способ изоляции работы агента. Влияет
  на реализацию BEH-33.
- **Q-12 · architects · blocking: false.** Определение команды запуска тестов. Влияет
  на реализацию BEH-19 и BEH-21.
- **Q-13 · architects · blocking: false.** Граница адаптера SDK и его подмена в тестах.
  Влияет на BEH-35 и BEH-36.
- **Q-14 · product · blocking: false.** Нужны ли в логе токены и стоимость вызовов.
