# Charter — sprc-runner на Claude Agent SDK

## 1. Контекст

Существующий инструмент spec-runner (соседний репозиторий автора) выполняет задачи по спекам
и обращается к модели через CLI-вызов `claude -p ...`, а также умеет вызывать codex.
Этот устав описывает чистую реализацию того же класса инструмента поверх Claude Agent SDK:
SDD-прогон «описание → спека/требования/задачи → цикл реализации каждой задачи → код, тесты,
логи и артефакты».

Источники устава — два discovery-брифа, зафиксированные по git-хешам во frontmatter:

- `discovery-customer` (`00-discovery/upstream.md`, customer-фрейм, status approved) — источник
  требований: цели, персоны, работы, FR, NFR, метрики, out-of-scope.
- `discovery-brief` (`00-discovery/brief.md`, engineer-фрейм) — системы, интерфейсы,
  архитектурные предпочтения, инженерные ограничения и риски.

Системы в периметре (по `discovery-brief#S-01` … `#S-10`): spec-runner как образец формата,
Claude Agent SDK как единственный харнесс, локальные файлы (спеки, `tasks.md`, логи, артефакты),
GitHub с кодом и PR, доступ к модели по личной подписке Anthropic. Все системы принадлежат
автору, неприкасаемых среди них нет.

Интерфейсы (по `discovery-brief#IF-01` … `#IF-07`): обмен только через файлы, без API, очередей
и прямого доступа к БД; вход — текст в командной строке или файл с описанием программы
(пишется один раз перед запуском и по ходу прогона не правится); промежуточные артефакты —
спека, требования, список задач; конечные артефакты — тесты и код в выбранной директории;
внутренний вид этих файлов задан скиллом в соседнем репозитории; контракт `tasks.md`
сохраняется как в spec-runner; API Anthropic не меняется, меняется только способ вызова —
через Claude Agent SDK.

## 2. Scope

**В периметре:** генерация спеки, требований и списка задач из входного описания; покадровый
цикл реализации по каждой задаче (сделал — ревью — тест) с отметкой в файле задач; CLI-запуск
и контроль прогона; конфигурация моделей по этапам в одном файле; проверяемые логи и артефакты;
возобновление прогона после паузы по лимитам подписки.

**Вне периметра:** см. раздел «Out of Scope» (OUT-01 … OUT-03).

**Правило разрешения коллизий ID:** классы CON и RK определены в обоих источниках с
пересекающимися номерами. Приоритет у источника требований (`discovery-customer`): он сохраняет
свои номера; элемент `discovery-brief` с тем же номером переносится в конец класса и помечен
пометкой «перенумерован». Все FR-NN и NFR-NN источника требований сохранены без изменений.

## 3. Goals

#### G-01: Чистая реализация spec-runner на штатных инструментах Claude

Сделать чистую реализацию spec-runner под Claude на встроенных инструментах, специально для
этого предназначенных, вместо текущего подхода через `claude -p ...`.

#### G-02: Однотипный подход для развития и сопровождения

Более однотипный подход к вызову модели и построению прогона, чтобы приложение было проще
развивать и сопровождать.

#### G-03: Эксперимент по юзабилити и ручному контролю

Это эксперимент: сравнить юзабилити и возможность ручного контроля приложения относительно
текущей реализации.

#### G-04: База для сравнения моделей

Получить возможность сравнивать модели и сохранять результаты прогонов, чтобы использовать их
при следующем выборе модели.

## 4. Personas

#### P-01: Коллеги — пользователи spec-runner

Вторичные пользователи: пока просто пользуются инструментом и только для своих пет-проектов.
Высказанные пожелания: оставить только Claude и сделать удобнее настройку используемых моделей.

#### P-02: Владелец решения

Решение о переделке принимает только автор — это его проект под другим его аккаунтом.
Все спорные вопросы устава закрывает он же.

#### P-03: Автор проекта (primary)

Primary-персона — сам автор проекта: пишет инструмент, запускает прогоны и потребляет
их результаты.

## 5. Jobs-to-be-done

#### J-01: Быстро получить POC из описания

Когда нужно быстро сделать POC приложения — написать спеку на основании предложенного запроса
или файла и получить по ней готовый результат.

#### J-02: Запускать и контролировать задачу

Запустить задачу и удобно контролировать её выполнение в терминале, а впоследствии и
в TUI-интерфейсе.

#### J-03: Встроить реализацию кода в пайплайн на Claude Agent SDK

Встроить в экосистему пайплайна на Claude Agent SDK удобное средство для реализации кода
с проверяемыми логами и артефактами.

#### J-04: Уйти от неформализованной ручной постановки задач

Сегодня это делается через постановку задачи Claude или Codex: такое трудно интегрировать
в пайплайн и трудно формализовать, тогда как в данном приложении реализован SDD.

## 6. Functional Requirements

#### FR-01: Модели по этапам задаются в конфигурации

Модель под задачу определяется в конфигурации (например, более продвинутая для написания спеки,
более простая для кодинга), все настройки — в одном файле.
Priority: Must. Traces: G-01, G-04.
Acceptance: на данном этапе модель в конфигурации выбирает пользователь.

#### FR-02: Лог выполнения с данными для анализа

Лог выполнения с данными для анализа — например, время выполнения задачи; логи нужны
в любом случае.
Priority: Must. Traces: G-01, G-04.
Acceptance: в логе видно время выполнения задачи.

#### FR-03: Спека, требования и задачи из входных данных, затем готовый результат

Написать спеку, требования и список задач на основании вводных данных (запроса или файла)
и затем по ним получить готовый результат — повторить весь функционал spec-runner.
Priority: Must. Traces: J-01.
Acceptance: работает так же, как это уже реализовано в spec-runner.
Примечание: объём «всего функционала» к сроку 1 декабря оспорен инженерным фреймом
(см. RK-06) и решается вопросом Q-01.

#### FR-04: Запуск и контроль задачи в терминале

Запуск задачи и контроль её выполнения в терминале.
Priority: Must. Traces: J-02.
Acceptance: контроль за задачей устраивает так же, как текущая реализация в spec-runner.

#### FR-05: TUI-интерфейс для запуска и контроля

TUI-интерфейс для запуска и контроля задачи — осознанно откладывается, но впоследствии
он нужен.
Priority: Should. Traces: J-02.
Acceptance: контроль за задачей устраивает так же, как текущая реализация в spec-runner.

#### FR-06: Проверяемые логи и артефакты

Проверяемые логи и артефакты по результатам реализации кода.
Priority: Must. Traces: J-03.
Acceptance: в логе и артефактах есть: время запуска задачи, идентификатор задачи, какая модель
использовалась, результаты тестов/ревью, сколько попыток (какая попытка), результат
(успех/неуспех, код ошибки, решение модели).

#### FR-07: Цикл реализации по каждой задаче

По каждой задаче из списка свой цикл реализации: сделал — ревью — тест; на выходе код, лог
и отметка в файле задач о выполнении.
Priority: Must. Traces: J-01, J-03.
Acceptance: рабочий код; тесты, заданные пунктом про тесты в требованиях и задачах, успешны;
соответствие спецификации. На выходе код, лог и отметка в файле задач о выполнении.
Примечание: исполнитель шага «ревью» (та же модель или другая) не определён — вопрос Q-03,
блокирующий проектирование цикла.

## 7. Non-Functional Requirements

#### NFR-01: Надёжность прогонов

Числовых требований к скорости/надёжности/безопасности нет: в числах не сказать, зависит
от объёма выполняемых задач, это пет-проект.
Acceptance: надёжность — 9 запусков из 10 завершаются успешно.

#### NFR-02: Недопустимо удаление готового кода

Недопустимо удаление готового кода.
Acceptance: проверять так же, как это реализовано в spec-runner.
Примечание: механическая защита признана непростой (RK-09).

#### NFR-03: Возобновляемость прогона

Прогон, остановленный из-за исчерпания лимитов подписки или прерванный иначе, продолжается
с места остановки, а не начинается заново и не падает.
Traces: CON-04, CON-12, RK-02.
Acceptance: после паузы и перезапуска уже выполненные задачи не выполняются повторно,
прогон доходит до конца списка задач.

#### NFR-04: Проверяемость ядра без сети

Ядро — чистая логика, тестируемая без обращения к сети и к Claude Agent SDK.
Traces: CON-11.
Acceptance: тесты ядра проходят при отключённой сети и без ключей доступа.

#### NFR-05: Изоляция работы агента

Агент работает только в каталоге своего прогона; изменения проверяются по диффу перед коммитом,
секреты не попадают в коммит.
Traces: CON-07, RK-03.
Acceptance: прогон не изменяет файлы вне своего рабочего каталога; дифф проверяется
до коммита.

#### NFR-06: Ограничение попыток на задачу

На задачу действует лимит попыток цикла «сделал — ревью — тест»; при исчерпании лимита задача
помечается неуспешной, прогон не зацикливается.
Traces: RK-04.
Acceptance: при постоянно падающем тесте прогон завершает задачу с отметкой неуспеха за
конечное число попыток.

#### NFR-07: Тесты запускает раннер, а не агент

Результат тестов фиксируется раннером (скриптом), а не со слов модели.
Traces: RK-05.
Acceptance: отметка об успехе задачи ставится только по коду возврата запуска тестов раннером.

#### NFR-08: Единый машиночитаемый формат логов

Логи всех прогонов пишутся в едином формате, пригодном для последующего сравнения моделей
внешним приложением.
Traces: G-04, FR-06, OUT-01, RK-10.
Acceptance: логи двух разных прогонов с разными моделями читаются одним парсером без
изменений кода парсера.

## 8. Constraints

#### CON-01: Только Claude Agent SDK

Используется только Claude Agent SDK, никакого codex или другого харнесса.

#### CON-02: Бюджет, люди, комплаенс и срок

Ограничений по бюджету, людям и обязательным интеграциям/политикам/комплаенсу нет — это
не enterprise; по срокам: первая версия к 1 декабря.

#### CON-03: Платформа и базовый стек

Работает локально на macOS (желательно и на Linux), стек — Python 3.12+ и uv (не pip).

#### CON-04: Лимиты подписки — пауза, а не падение

Модель доступна по личной подписке Anthropic — упираемся в лимиты подписки; при исчерпании
прогон должен вставать на паузу и продолжаться, а не падать.

#### CON-05: Нет платной инфраструктуры

Платной инфраструктуры нет.

#### CON-06: Один разработчик в свободное время

Разработчик один, работает в свободное время; первая рабочая версия — к первому декабря.

#### CON-07: Файлы DarkFactory не трогать

Файлы DarkFactory в репозитории (`profiles/`, `scripts/review/`, `spec-runner.config.yaml`,
`.github/`) не трогать.

#### CON-08: Нет ограничений по политике доступа

Ограничений по политике нет: сеть, доступы и секреты ничем не ограничены.
Перенумерован из `discovery-brief#CON-01` по правилу разрешения коллизий (раздел 2).

#### CON-09: Локальный запуск без чувствительных данных

Код запускается на локальной машине, чувствительных данных нет.
Перенумерован из `discovery-brief#CON-02` по правилу разрешения коллизий (раздел 2).

#### CON-10: Обязательный инструментарий качества

ruff (длина строки 88), pyrefly, обязательные type hints, pytest; асинхронный код — через anyio.

#### CON-11: Ядро и тонкие адаптеры, версия SDK запинена

Ядро — чистая логика; Claude Agent SDK, файлы и git — за тонкими адаптерами на краях.
Версия Claude Agent SDK пинится, все вызовы SDK идут через один адаптер.

#### CON-12: Состояние прогона — в файлах

Состояние прогона хранится в файлах (JSON) в каталоге прогона, чтобы прерванный прогон можно
было продолжить.

#### CON-13: Сначала CLI, TUI позже

Сначала CLI, TUI — позже.

#### CON-14: Из spec-runner переносится только формат tasks.md

От spec-runner берём только формат `tasks.md` — он остаётся таким же, как в соседнем
репозитории; остальной код пишем заново. Код spec-runner не переиспользуется: там есть вызовы
codex, который использовать не будем, и обращение к модели идёт через `claude -p`.

#### CON-15: Правила разработки и простота

Формальных ADR в репозитории нет; обязательны правила разработки автора. Решения — просто
и читаемо, без лишних абстракций.

#### CON-16: Тесты к каждому изменению

Новая функция — с тестами, исправление — с регрессионным тестом.

#### CON-17: Обмен данными только через файлы

Данные ходят только через файлы — никаких API, очередей или прямого доступа к БД.

## 9. Success Metrics

#### M-01: Доля успешных новых проектов

Из 10 новых проектов на разработку приложений 9 успешных — это показывает, что приложение
на основе SDD эффективно работает и производит программные продукты.
Traces: G-01.

#### M-02: Сквозной сценарий без падений

Сценарий работает от написания спеки до работающего кода: из 10 запусков подряд ни одного
падения; текущее значение точно не зафиксировано — последний раз было 13 запусков, неуспешные
не отслеживались.
Target: 10 из 10 запусков подряд без падения.
Traces: G-01.
Примечание: цель оспорена инженерным фреймом (RK-07: сначала базовая линия, для первой версии
8 из 10) — решается вопросом Q-02.

#### M-03: Полнота логов прогона

Доля прогонов, лог которых содержит полный набор полей из критериев FR-06 (время запуска,
идентификатор задачи, модель, результаты тестов/ревью, номер попытки, результат).
Target: 100% прогонов первой версии.
Traces: G-04, FR-06, NFR-08.

## 10. Out of Scope

#### OUT-01: Самостоятельное сравнение и анализ моделей

Приложение не должен само тестировать модели и само делать сравнение и анализ результатов —
это делает другое приложение; здесь только артефакты и логи для него (сам код и лог выполнения).

#### OUT-02: Вариант «только codex»

Вариант «только codex» — это другой проект, здесь он не делается.

#### OUT-03: TUI в первой версии

TUI-интерфейс не входит в первую версию к 1 декабря: FR-05 имеет приоритет Should и
реализуется после CLI (CON-13).

## 11. Risks

#### RK-01: Оверинжиниринг

Оверинжиниринг, переусложнение решения.
Митигация: CON-15 (простота, без лишних абстракций), минимальный срез функционала к сроку.

#### RK-02: Лимиты подписки заканчиваются посреди прогона

Лимиты подписки заканчиваются посреди прогона.
Митигация: пауза и продолжение с места остановки (CON-04, CON-12, NFR-03).

#### RK-03: Агент портит файлы вне задачи или коммитит секреты

Агент портит файлы вне задачи или коммитит секреты.
Митигация: работа только в своём каталоге, проверка диффа перед коммитом (NFR-05, CON-07).

#### RK-04: Зацикливание на падающих тестах

Прогон зацикливается на падающих тестах.
Митигация: лимит попыток на задачу (NFR-06).

#### RK-05: Агент рапортует успех без проверки

Агент рапортует успех без фактической проверки.
Митигация: тесты запускает скрипт, а не агент (NFR-07, CON-16).

#### RK-06: Полный паритет с spec-runner к 1 декабря нереален

Повторить весь функционал spec-runner к 1 декабря нереально целиком: заказчик хочет полный
паритет, инженер считает реальным только минимальный срез — спека → задачи → цикл одной задачи
с тестами и логом, остальное после. Решение за владельцем решения (P-02), см. Q-01.

#### RK-07: Цель «10 из 10» поставлена без базовой линии

Цель «10 из 10 без падений» поставлена без базовой линии: заказчик хочет 10/10, инженер
предлагает сначала замерить базовую линию, для первой версии цель 8 из 10. Решение
за владельцем решения (P-02), см. Q-02.

#### RK-08: Не определён ревьюер в цикле задачи

Не решено, кто ревьюит в цикле «сделал — ревью — тест» — тот же Claude или другая модель.
Блокирует проектирование цикла (FR-07), см. Q-03.

#### RK-09: Защита от удаления готового кода механически непроста

Защита от удаления уже готового кода механически непроста, а требование NFR-02 жёсткое.

#### RK-10: Недооценён единый формат логов

Единый формат логов для сравнения моделей в инженерном брифе недооценён по трудоёмкости
(NFR-08, M-03).

#### RK-11: Bus-factor 1

Единственный разработчик — автор; заменить его некем, при его выпадении проект встаёт
(CON-06).

#### RK-12: Claude Agent SDK меняет API

Claude Agent SDK меняет API между версиями.
Митигация: пин версии, все вызовы за одним адаптером (CON-11).
Перенумерован из `discovery-brief#RK-01` по правилу разрешения коллизий (раздел 2).

## 12. Open Questions

#### Q-01: Объём первой версии к 1 декабря
