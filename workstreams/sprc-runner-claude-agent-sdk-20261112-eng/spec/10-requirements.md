# Требования — sprc-runner на Claude Agent SDK

## 1. Назначение документа

Документ разворачивает устав (`00-charter.md`, версия 2, approved) в проверяемые требования
к первой версии инструмента. Устав — единственный верхний источник; дискавери-брифы
(`00-discovery/upstream.md`, `00-discovery/brief.md`) видны через него и цитируются только
как происхождение идентификаторов.

Правила работы с идентификаторами:

- FR-01 … FR-07 и NFR-01 … NFR-02 пришли из источника требований (`discovery-customer`)
  и сохранены дословно по номеру, приоритету и смыслу приёмки; здесь они уточнены
  до проверяемой формулировки, но не переопределены.
- NFR-03 … NFR-08 введены уставом и сохранены по номерам.
- FR-08 … FR-11 и NFR-09 … NFR-12 введены на этом этапе: это требования, вытекающие
  из ограничений и интерфейсов устава, которые в нём зафиксированы как CON/IF,
  но не были выражены как требование.
- Классы G, J, P, CON, RK, M, OUT используются в трассировке в нумерации устава.

## 2. Границы первой версии

В периметре первой версии: подготовка артефактов (спека, требования, список задач)
из входного описания; цикл реализации по каждой задаче «сделал — ревью — тест»;
CLI-запуск и контроль; конфигурация моделей по этапам в одном файле; машиночитаемые логи
и артефакты; пауза и возобновление прогона.

Вне периметра первой версии: TUI (OUT-03, FR-05 — Should); самостоятельное сравнение
и анализ моделей (OUT-01); любой харнесс, кроме Claude Agent SDK (OUT-02, CON-01).

Открыт вопрос Q-01 о том, означает ли «весь функционал spec-runner» (FR-03) полный паритет
или минимальный сквозной срез. До его закрытия требования сформулированы так, чтобы
минимальный сквозной срез был полностью покрыт, а паритет добавлялся расширением
набора задач, а не переделкой контрактов. Это допущение A-01 (раздел 7).

## 3. Функциональные требования

#### FR-01: Модели по этапам задаются в конфигурации

**Priority**: Must
**Traces**: charter#FR-01, G-01, G-04, P-01
**Происхождение ID**: discovery-customer#FR-01

Модель под каждый этап прогона определяется в конфигурации; все настройки прогона лежат
в одном файле. Этапы, для которых модель задаётся раздельно: подготовка спеки и требований,
составление списка задач, реализация кода, ревью. Значения выбирает пользователь;
инструмент не подбирает модель сам.

**Acceptance**:
- В конфигурации есть отдельный ключ модели для каждого из перечисленных этапов;
  изменение значения меняет модель, которой выполняется этап, без правок кода.
- Все настройки прогона (модели, лимит попыток, каталоги, параметры логирования) читаются
  из одного файла; второго источника настроек нет.
- При отсутствии файла, неизвестном ключе или незаполненной модели этапа прогон
  не стартует и печатает сообщение с именем проблемного ключа.
- Фактически применённая модель каждого этапа попадает в лог прогона (FR-06).

#### FR-02: Лог выполнения с данными для анализа

**Priority**: Must
**Traces**: charter#FR-02, G-01, G-04, NFR-08
**Происхождение ID**: discovery-customer#FR-02

Прогон пишет лог выполнения, пригодный для последующего анализа внешним приложением.
Минимум данных — временные характеристики: момент старта и завершения прогона, момент старта
и завершения каждой задачи, длительность задачи и прогона.

**Acceptance**:
- В логе для каждой задачи видно время выполнения.
- В логе видно время выполнения прогона целиком.
- Лог пишется по ходу прогона, а не только при успешном завершении: после аварийной
  остановки записи по уже завершённым задачам сохраняются.

#### FR-03: Спека, требования и задачи из входных данных, затем готовый результат

**Priority**: Must
**Traces**: charter#FR-03, J-01, IF-02, IF-03, IF-04
**Происхождение ID**: discovery-customer#FR-03

По входному описанию (строка в командной строке или файл) инструмент порождает спеку,
требования и список задач, а затем по этому списку получает готовый результат — код и тесты
в выбранной директории. Этапы подготовки идут последовательно, каждый следующий опирается
на артефакт предыдущего.

**Acceptance**:
- Из одного входного описания без дополнительного участия пользователя получаются три
  артефакта подготовки: спека, требования, список задач — в каталоге прогона.
- Список задач служит входом для цикла реализации (FR-07); задач в нём не меньше одной.
- Сквозной сценарий «описание → артефакты подготовки → код и тесты» проходит целиком
  на эталонном входном описании.

**Примечание**: объём «всего функционала spec-runner» к сроку 1 декабря оспорен (RK-06),
решается вопросом Q-01.

#### FR-04: Запуск и контроль задачи в терминале

**Priority**: Must
**Traces**: charter#FR-04, J-02, CON-13
**Происхождение ID**: discovery-customer#FR-04

Прогон запускается одной командой CLI и наблюдаем из терминала во время работы: видно,
какой этап или задача выполняется сейчас, какая это попытка и чем закончилась предыдущая.

**Acceptance**:
- Команда запуска принимает входное описание и целевой каталог (FR-08) и стартует прогон.
- Во время работы в терминал выводятся: текущий этап или идентификатор текущей задачи,
  номер попытки, исход завершённой задачи (успех/неуспех).
- Код возврата процесса отличает успешный прогон от прогона с неуспешными задачами
  и от аварийной остановки.
- Прерывание пользователем (Ctrl-C) оставляет состояние прогона в виде, пригодном
  для возобновления (FR-09).

#### FR-05: TUI-интерфейс для запуска и контроля

**Priority**: Should
**Traces**: charter#FR-05, J-02, CON-13, OUT-03
**Происхождение ID**: discovery-customer#FR-05

TUI-интерфейс для запуска и контроля задачи. Осознанно откладывается за пределы первой
версии, но требуется впоследствии.

**Acceptance**:
- В TUI видны статус текущей задачи (этап, номер попытки, исход) и её лог; задачу можно
  остановить и перезапустить из TUI.
- Требование не входит в приёмку первой версии (OUT-03); реализация не должна требовать
  изменения контрактов логов и состояния прогона, заданных FR-06 и FR-09.

#### FR-06: Проверяемые логи и артефакты

**Priority**: Must
**Traces**: charter#FR-06, J-03, G-04, M-03, NFR-08
**Происхождение ID**: discovery-customer#FR-06

По результатам реализации кода остаются логи и артефакты, по которым можно проверить, что
и как было сделано, не обращаясь к модели повторно.

**Acceptance**: для каждой задачи в логе/артефактах присутствуют все поля:
- время запуска задачи;
- идентификатор задачи;
- использованная модель;
- результаты тестов и ревью;
- номер попытки и общее число сделанных попыток;
- результат: успех/неуспех, код ошибки, решение модели.

Дополнительно:
- Поля заполнены для 100% задач завершённого прогона (M-03); пропуск поля считается дефектом.
- Артефакты лежат в каталоге прогона и читаются без запуска инструмента.

#### FR-07: Цикл реализации по каждой задаче

**Priority**: Must
**Traces**: charter#FR-07, J-01, J-03, NFR-06, NFR-07, FR-10
**Происхождение ID**: discovery-customer#FR-07

По каждой задаче из списка выполняется собственный цикл «сделал — ревью — тест». На выходе
задачи: код, запись в логе и отметка о выполнении в файле задач.

**Acceptance**:
- Шаги цикла выполняются в порядке: реализация → ревью → запуск тестов.
- Задача считается выполненной только при успешном прогоне тестов, запущенных раннером
  (NFR-07), и при пройденном ревью.
- При неуспехе цикл повторяется до лимита попыток (NFR-06); каждая попытка попадает
  в лог отдельной записью (FR-06).
- Код соответствует спецификации и требованиям, порождённым FR-03.
- После успешной задачи в файле задач стоит отметка о выполнении (FR-10).

**Примечание**: исполнитель шага «ревью» не определён — вопрос Q-03, блокирующий
проектирование цикла.

#### FR-08: Вход прогона и целевой каталог

**Priority**: Must
**Traces**: charter#CON-17, IF-01, IF-02

Прогон принимает входное описание двумя способами: как текст в командной строке
(несколько предложений) или как путь к файлу с подробным описанием на несколько страниц
(функции, ограничения, критерии успеха, масштабируемость). Результат — код и тесты —
кладётся в указанный целевой каталог; по умолчанию это выделенный каталог `.sdd-runs/`
внутри каталога запуска, отдельный от файлов DarkFactory (CON-07) и прочего содержимого
каталога запуска.

**Acceptance**:
- Оба способа ввода дают одинаковый дальнейший сценарий; различие только в источнике текста.
- Входное описание фиксируется в каталоге прогона в неизменном виде и не правится
  по ходу прогона.
- Целевой каталог задаётся параметром; при его отсутствии результат кладётся в каталог
  по умолчанию `.sdd-runs/`, а не вперемешку с содержимым каталога запуска; файлы
  DarkFactory (CON-07) не затрагиваются.
- Обмен данными идёт только через файлы: ни API, ни очередей, ни прямого доступа к БД
  (CON-17).

#### FR-09: Пауза и возобновление прогона

**Priority**: Must
**Traces**: charter#NFR-03, CON-04, CON-12, RK-02, FR-04

Прогон можно остановить (по исчерпании лимитов подписки, по прерыванию пользователем
или из-за сбоя) и затем продолжить с места остановки отдельной командой, не начиная заново.

**Acceptance**:
- Состояние прогона хранится в файлах JSON в каталоге прогона и обновляется после каждой
  завершённой задачи и каждой завершённой попытки.
- Команда возобновления, запущенная на каталоге прогона, продолжает со следующей
  невыполненной задачи; уже выполненные задачи повторно не выполняются.
- Исчерпание лимитов подписки приводит к паузе с внятным сообщением и ненулевым кодом
  возврата, а не к падению с трассировкой.
- После паузы и перезапуска прогон доходит до конца списка задач.

#### FR-10: Контракт файла задач

**Priority**: Must
**Traces**: charter#CON-14, IF-06, FR-07

Файл `tasks.md` остаётся таким же, как в соседнем репозитории spec-runner: тот же формат
записи задач и та же форма отметки о выполнении. Формат — внешний контракт, инструмент
его не расширяет в первой версии.

**Acceptance**:
- `tasks.md`, порождённый инструментом, читается инструментарием и глазами так же,
  как `tasks.md` из spec-runner.
- Отметка о выполнении ставится в том же виде, что в spec-runner.
- Отметка проставляется только после успешного завершения задачи (FR-07).

#### FR-11: Форматы артефактов подготовки

**Priority**: Must
**Traces**: charter#IF-05, FR-03

Внутренний вид спеки, требований и списка задач задан скиллом в соседнем репозитории;
инструмент порождает артефакты подготовки в этих форматах, а не в собственных.

**Acceptance**:
- Спека, требования и список задач соответствуют структуре, описанной скиллом-источником.
- Источник формата зафиксирован в репозитории по пути и версии (см. Q-06), а не
  по устной договорённости.

## 4. Нефункциональные требования

#### NFR-01: Надёжность прогонов

**Priority**: Must
**Traces**: charter#NFR-01, M-01, M-02
**Происхождение ID**: discovery-customer#NFR-01

Числовых требований к скорости и безопасности нет — это пет-проект, величины зависят
от объёма задач. Зафиксирована только надёжность завершения прогона.

**Acceptance**:
- Не менее 9 из 10 запусков завершаются успешно.
- Целевое значение для приёмки первой версии уточняется вопросом Q-02 (10/10 против 8/10
  с предварительным замером базовой линии).

#### NFR-02: Недопустимо удаление готового кода

**Priority**: Must
**Traces**: charter#NFR-02, RK-09, NFR-05
**Происхождение ID**: discovery-customer#NFR-02

Готовый код, созданный на предыдущих задачах прогона, не должен удаляться последующими
задачами.

**Acceptance**:
- Проверка выполняется так же, как реализовано в spec-runner.
- Удаление ранее созданного файла или значимое сокращение его содержимого вне явного
  предмета задачи фиксируется до коммита и не проходит молча.
- Механика проверки — предмет проектирования (RK-09, Q-09).

#### NFR-03: Возобновляемость прогона

**Priority**: Must
**Traces**: charter#NFR-03, CON-04, CON-12, RK-02, FR-09

Прогон, остановленный из-за исчерпания лимитов подписки или прерванный иначе, продолжается
с места остановки, а не начинается заново и не падает.

**Acceptance**:
- После паузы и перезапуска уже выполненные задачи не выполняются повторно,
  прогон доходит до конца списка задач.
- Проверяется тестом, имитирующим обрыв между задачами и после неуспешной попытки.

#### NFR-04: Проверяемость ядра без сети

**Priority**: Must
**Traces**: charter#NFR-04, CON-11

Ядро — чистая логика, тестируемая без обращения к сети и к Claude Agent SDK; SDK, файловая
система и git вынесены за тонкие адаптеры на краях.

**Acceptance**:
- Тесты ядра проходят при отключённой сети и без ключей доступа.
- В модулях ядра нет прямых вызовов SDK, git и сетевых клиентов.

#### NFR-05: Изоляция работы агента

**Priority**: Must
**Traces**: charter#NFR-05, CON-07, RK-03

Агент работает только в каталоге своего прогона и целевом каталоге результата; изменения
проверяются по диффу перед коммитом, секреты в коммит не попадают.

**Acceptance**:
- Прогон не изменяет файлы вне своего рабочего каталога.
- Файлы DarkFactory (`profiles/`, `scripts/review/`, `spec-runner.config.yaml`, `.github/`)
  не изменяются ни при каких условиях (CON-07).
- Дифф проверяется до коммита; попытка внести изменение за пределами разрешённых путей
  останавливает коммит.

#### NFR-06: Ограничение попыток на задачу

**Priority**: Must
**Traces**: charter#NFR-06, RK-04, FR-01, FR-07

На задачу действует лимит попыток цикла «сделал — ревью — тест»; при исчерпании лимита
задача помечается неуспешной, прогон не зацикливается.

**Acceptance**:
- При постоянно падающем тесте прогон завершает задачу отметкой неуспеха за конечное
  число попыток.
- Значение лимита задаётся в конфигурации (FR-01) и имеет значение по умолчанию.
- Конкретное значение по умолчанию и поведение прогона после исчерпания лимита
  (остановка или переход к следующей задаче) уточняются вопросом Q-04.

#### NFR-07: Тесты запускает раннер, а не агент

**Priority**: Must
**Traces**: charter#NFR-07, RK-05, FR-07

Результат тестов фиксируется раннером, а не со слов модели.

**Acceptance**:
- Отметка об успехе задачи ставится только по коду возврата запуска тестов раннером.
- Утверждение модели об успехе без фактического запуска тестов не влияет на исход задачи.
- В логе сохраняется код возврата запуска тестов (FR-06).

#### NFR-08: Единый машиночитаемый формат логов

**Priority**: Must
**Traces**: charter#NFR-08, G-04, FR-02, FR-06, M-03, OUT-01, RK-10

Логи всех прогонов пишутся в едином машиночитаемом формате, пригодном для последующего
сравнения моделей внешним приложением. Само сравнение здесь не делается (OUT-01).

**Acceptance**:
- Логи двух разных прогонов с разными моделями читаются одним парсером без изменений
  кода парсера.
- Формат логов описан в репозитории и версионирован: поле версии схемы присутствует
  в записи лога.

#### NFR-09: Стек и инструментарий качества

**Priority**: Must
**Traces**: charter#CON-03, CON-05, CON-09, CON-10, CON-15

Инструмент работает локально на macOS, стек — Python 3.12+ и uv (не pip). Обязательны ruff
с длиной строки 88, pyrefly, type hints во всём коде, pytest; асинхронный код — через anyio.
Решения простые и читаемые, без лишних абстракций (RK-01).

**Acceptance**:
- Зависимости и запуск — через uv; pip в инструкциях и скриптах не используется.
- Запуск и тесты выполняются на локальной машине без платной инфраструктуры и внешних
  сервисов (CON-05); чувствительные данные для работы не требуются (CON-09).
- ruff, pyrefly и pytest проходят без ошибок на основной ветке.
- Публичные функции и методы аннотированы типами.

#### NFR-10: Пин версии SDK и единая точка вызова

**Priority**: Must
**Traces**: charter#CON-01, CON-11, RK-12

Версия Claude Agent SDK зафиксирована (пин), все обращения к SDK идут через один адаптер.
Другие харнессы, включая codex, не используются (CON-01, OUT-02).

**Acceptance**:
- Версия SDK указана точным значением в описании зависимостей.

## 7. Допущения

- **A-01.** До ответа на Q-01 «весь функционал spec-runner» в FR-03 читается как сквозной
  срез «описание → спека/требования/задачи → цикл задач с тестами и логом». Расширение
  до полного паритета не меняет контракты FR-06, FR-09, FR-10.
- **A-02.** Эталонное входное описание для приёмочных проверок готовит владелец решения
  (P-02); оно фиксируется в репозитории как тестовые данные.
- **A-03.** До ответа на Q-04 лимит попыток на задачу принимается равным значению
  по умолчанию в конфигурации и не блокирует разработку.
- **A-04.** Ревью в FR-07 считается обязательным шагом цикла независимо от того, кто его
  исполняет; ответ на Q-03 меняет исполнителя, а не наличие шага.
